## Writing and Git history

- Write as a developer explaining work to another developer. Use plain, specific English. Avoid marketing language, generic praise, repetitive summaries, and unnecessary emoji or badges.
- Keep README introductions factual. Explain what works, how to run it, and what is still missing. Do not claim a test, feature, performance result, or deployment unless there is evidence.
- Prefer short commit subjects such as `fix: correct project navigation` or `docs: update setup steps`. Describe the change, not the effort. Avoid vague `update` messages and long release-style subjects.
- Add a commit body only when the reason, migration steps, risks, or test evidence need explanation. Put extensive review notes in a PR or a dedicated document, not in every small commit.
- Keep unrelated changes in separate commits when practical. Do not split one atomic fix just to create more commits.
- Do not rewrite published history, remove AI attribution, change release records, or force-push for cosmetic cleanup.
- Preserve security, privacy, attribution, and operational documentation. Never invent authorship or remove meaningful warnings to make a README look cleaner.
- Report which checks actually ran. If something could not be verified, say so.
